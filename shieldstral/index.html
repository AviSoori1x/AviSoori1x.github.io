Technical report walkthrough

Shieldstral How a 3B safety classifier takes its policy at inference time

I was a core contributor to this model.

Shieldstral is Mistral's open-weight, policy-adaptive multimodal safety classifier. The weights are Apache 2.0 and the technical report is public, so this page walks through the model, the data pipeline behind it, and the reported results.

Most guardrail models ship with their list of harms already decided. You get the categories the authors chose, and if your product does not fit them you either fine-tune or live with the mismatch. Shieldstral takes a different route: moderation becomes a single yes/no question, and the question arrives at inference time as plain text. The report argues that this formulation, together with the data pipeline, is what lets a 3B model match much larger systems on the reported averages.

Everything here comes from the technical report and the model card. The numbers the figures display are parsed programmatically out of those two sources rather than typed in by hand. Where I am giving my own read rather than reporting the paper, I say so.

Contents
    § 01

    The problem with a fixed list of harms

    A guardrail model sits between your users and your language model and catches content you do not want flowing in either direction. The usual design is a classifier trained against a fixed taxonomy: content goes in, a label from a fixed vocabulary comes out. In the report's own comparison table, LlamaGuard-4 and Qwen3Guard work that way. ShieldGemma is listed as adaptive and returns a score rather than a label, so the field is not uniform, but a fixed category set is still the common case.

    The report separates the resulting difficulty into a training problem and a deployment problem.

    The training problem is that public safety datasets do not agree with each other. They differ in label formats, category taxonomies and annotation conventions, and the report is direct that there is no one-size-fits-all taxonomy to model. Commit to a single category set and every dataset has to be forced through a mapping to reach it. Preserving each dataset's decision boundary through that mapping is described as a central challenge, not a solved problem.

    The deployment problem is the one operators feel. A fixed model returns the same label regardless of who is asking or why. The report's example: content that is perfectly appropriate for a cybersecurity research tool could be deeply harmful on a platform providing mental health support. A fixed classifier cannot express that, because the thing that changed is not the content.

    My read, not the paper

    You can work around this, but neither workaround is free. Fine-tuning a guardrail per surface costs a training run and another checkpoint every time the policy moves. Post-processing with a per-surface category allowlist only helps when the policy you want can be expressed in categories the model already exposes.

    § 02

    One question at a time

    Shieldstral answers one yes/no question about one document, and the caller supplies the question. That reformulation is the spine of the paper.

    The core idea

    Content moderation is reduced to binary question answering. The safety policy stops being a property of the model's weights and becomes a string in the prompt.

    This changes two things: how the training datasets combine, and how policy is supplied at inference time.

    On the data side, if every task is "does this document satisfy this query, yes or no", then a binary toxicity set, a fifteen-category hate speech taxonomy, a jailbreak detection set and a refusal-detection corpus all become the same kind of row. Each dataset keeps its own processor, which does the category mapping and label conversion, but the training objective is shared. The report's claim is that heterogeneous datasets with divergent taxonomies can be consolidated under one framework, not that the conversion is lossless.

    On the inference side, the query is text rather than a class ID, so the model can be pointed at policies that were never training labels. Section 10 covers how the authors tested that, using an evaluation taxonomy built specifically to differ from the training one. That evidence is about generalising to an independently designed taxonomy. It is not a guarantee that any query you write will work.

    The figure below shows the two contrastive settings side by side, using labelled examples from the report. One holds the document fixed and changes the query. The other holds the query fixed and changes the document to a different kind of harm. The verdict flips in both.

    The fixed-query case is the harder test. Both documents in it are unsafe by any ordinary reading, and only one matches the question being asked. A model that has learned "this text feels dangerous" answers yes to both. The contrastive data in stages two and three targets exactly that failure.

    § 03

    The shape of a request

    Every call is a fixed system message plus a user message carrying three tagged fields. The system message establishes the meta-task and restricts the answer to yes or no. It is the same string on every request.

    • <Instruct> carries the high-level framing: the evaluation context and the strictness level. The report expects it to be constant across a dataset or task, and the model card sharpens that into advice, keep it constant across a product surface.
    • <Query> is the condition being tested, phrased as one yes/no question. This is the field that changes per policy.
    • <Document> is the content: a user prompt, a model response, a formatted prompt and response pair, or an image with optional accompanying text.

    Framing and question are separate fields because they do separate jobs. Training assigns different strictness tiers to different datasets and varies the instruction wording within each, which is how strictness language gets any meaning at all. What the report does not do is isolate the effect: there is no ablation measuring how far a strictness-only change to <Instruct> moves the score.

    The catch

    One question per call. The model emits a single token, so it cannot answer three policies at once. The model card's own guidance is to issue one query per policy, or, for an overall verdict, to list the categories in the instruction and ask one broad question. The second option tells you something is wrong without telling you which policy tripped.

    § 04

    Two logits and nothing else

    Training uses ordinary cross-entropy over the full vocabulary at the output position. It is a normal language model being taught that the next token is "yes" or "no".

    Inference only unembeds two token ids. You read the logits for "yes" and "no", call them z_yes and z_no, and softmax over just those two. The result is the model's relative preference for yes over no, a continuous value between 0 and 1. The report thresholds it at 0.5.

    Worth being precise about what that score is and is not. It is a renormalised comparison of two logits. Neither the report nor the model card claims it is calibrated across datasets or across prompt phrasings, so treat 0.5 as the reported default rather than a number with inherent meaning on your data.

    The practical consequence is cost. A verdict is one forward pass and one token. The report says GPT-OSS-Safeguard and Nemotron-3.5-Safety generate a reasoning trace before answering, which significantly reduces inference efficiency. There is a wrinkle worth flagging: the same report's comparison table lists Nemotron-3.5-Safety's output as a label rather than reasoning plus label, so the two statements sit slightly awkwardly together.

    You also get a threshold you can move, because the output is a score rather than a hard label. Whether a competing guardrail offers the same control depends on whether its implementation exposes scores or logits, which is a separate question from whether its taxonomy is fixed.

    The catch

    There is no reasoning trace, so when the model flags something you disagree with there is nothing to read. Debugging a false positive means editing the query in controlled ways and watching the score move.

    § 05

    Fifty-four million rows

    Most of the report is about data construction, and the authors name that as the contribution. The pipeline produces roughly 54.1 million samples: 45.2M open-source text, 4.4M synthetic contrastive text, and 4.5M multimodal. Open-source text dominates by an order of magnitude. The two smaller buckets are about the same size as each other.

    Four stages produce that pile. Stage one standardises the input format across incompatible sources. Stage two builds contrastive pairs out of labels that already exist. Stage three generates new content and query pairs for finer distinctions. Stage four supplements the limited image safety data. The next three sections take them in turn.

    § 06

    Stage one: making incompatible datasets speak one language

    Every source dataset gets its own processor, manually designed from that dataset's existing description. A processor defines the labelling logic, the category mappings, and the instruction templates appropriate to that dataset's task and annotation conventions.

    Each processor holds a pool of phrasings rather than one fixed template.

    Instruction templates carry strictness

    An LLM generates multiple paraphrase variants of each processor's instruction templates. The variants encode the task framing, such as safety classification versus quality assessment; the intended strictness level, strict, moderate or lenient; and domain-specific context such as multilinguality or adversarial framing.

    Strictness is assigned per dataset. Adversarial jailbreak data and visual safety data get strict templates, because subtle harms there must be flagged aggressively. General safety, hate speech and toxicity get moderate templates, balancing sensitivity against false positives. Response quality and dialogue moderation get lenient templates, where only clearly harmful content should be flagged. Different tiers give the model examples with different intended decision boundaries, which is the report's stated reason for doing it this way.

    Queries and document formats are pooled too

    Query templates come in three task types, each with multiple paraphrase variants: category-specific queries for datasets with fine-grained taxonomies, binary queries asking about overall safety without naming a category, and dedicated refusal-detection queries.

    Prompt and response pairs are rendered through one of seven format families, including bracketed, XML-style, Markdown, role-based, conversational and minimal forms. The report's stated aim is to avoid depending on a single delimiter convention and to generalise better to real dialogue formats.

    Resampling across epochs

    During training, each sample draws an instruction phrasing and a query variant from its processor's pools. Prompt and response examples additionally draw one of the seven document formats. So the same content shows up under different framings across epochs.

    Resampling reduces the chance that the model can attach a label to one fixed wording. The intended effect is generalisation across phrasing, which is what an operator is relying on when they write a policy in their own words rather than the authors'.

    § 07

    Stages two and three: teaching discrimination, not categories

    Unification alone already transfers further than you might expect. The public-data checkpoint reaches 61.1 F1 on the fine-grained taxonomy validation set without ever seeing a query or a label from that taxonomy. Adding the generated data takes it to 84.4. So stage three is not rescuing a broken model, it is buying a large increment on a model that already partially works.

    Stage two varies queries over content that already carries labels. Stage three generates new content and query pairs to reach distinctions the public data does not contain.

    Stage two: contrast from data you already have

    The move is to generate training pairs from the same content by varying the query, which teaches discrimination between categories rather than detection of unsafety.

    For each piece of harmful content the pipeline emits positives at several granularities: a coarse binary query, a category-specific query, and where applicable a target-group-specific query that narrows from violence in general to violence toward a particular group.

    Negatives come three ways. Category-based hard negatives pair content violating category A with queries about categories B, C and so on, which are genuinely absent. Demographic-based negatives pair content targeting one group with queries about unrelated groups. Safe-content negatives pair genuinely safe samples with ordinary harmfulness queries.

    The first two are the interesting ones: the document is unsafe and the correct answer is still no.

    Two supporting details. Contrastive construction produces more negatives than positives, since any absent category can serve as a hard negative while positives are limited to what the annotations assert, so each positive is duplicated with independently paraphrased instruction and query per copy to raise the positive share. Separately, because public safety datasets contain incorrect labels, an open-source LLM cross-validates them at the binary and per-category levels, and disagreements are dropped.

    Stage three: generating the hard cases

    Public datasets typically lack fine-grained safety categories with subtle distinctions, so the pipeline generates them.

    A training taxonomy is defined first: 11 super classes and 73 leaf categories, derived from the 11 source taxonomies present in the open-source datasets. An LLM is then given a safe source text, a target category and a sibling category, and returns three things in one call. An unsafe rewrite exhibiting the target while avoiding the sibling, a query about the target, and a query about the sibling.

    One call, two training rows. The positive pairs the rewrite with the target query and the answer yes. The negative pairs the identical rewrite with the sibling query and the answer no. The report calls this the iso-content setting: content held fixed, query varied.

    The stated intent is to train the skill of separating policy-relevant from policy-irrelevant content, rather than coverage of a fixed policy list, on the grounds that enumerating every conceivable policy is infeasible.

    The queries differ in origin as well. Stage-one queries are drawn from pre-authored template pools and mostly separate broad category boundaries. Stage-three queries are written fresh with each rewrite and capture subtle, context-specific distinctions between closely related categories, which pushes the model toward the semantics of the query rather than coarse category cues.

    The hierarchy trick

    Because the taxonomy is hierarchical, content violating a leaf also violates every ancestor up to the super class. The pipeline reuses the same rewrite with ancestor-level queries, adding positive rows at no extra generation cost and teaching the model to recognise the violation at several granularities.

    § 08

    Stage four: the image problem

    Image safety data is harder to get than text. Public image moderation datasets are fewer, smaller, and cover narrower taxonomies. And the trick behind stage three does not carry over, because unsafe images cannot simply be generated synthetically by an LLM the way unsafe text can be rewritten.

    The pipeline compensates in several places rather than one.

    Source labels are mapped from their native formats, integer class indices, object-detection annotations, binary flags, onto a unified taxonomy yes/no question, with images drawn from three pools: violation datasets, clean datasets, and general-classification datasets. That last pool is the important one. General-purpose image classification and object-detection datasets supply a large volume of diverse, naturally safe images that serve as high-quality negatives.

    Diversity is then pushed onto the text side, since modifying images at scale is difficult. Roughly 2,000 query phrasings are generated from a fixed fourteen-subcategory visual moderation taxonomy covering NSFW, violence, hate and illegal content. About 30% are inverse formulations, phrased as "is this image safe from violence" rather than "does this image contain violence", so the model sees both polarities of the same category.

    A vision-language reranker then scores every image and query pair, filtering mislabelled source data and LLM hallucinations. The thresholds are asymmetric: looser on the rare violation samples so they survive, stricter on the abundant negatives. An LLM also generates hard negatives, pairing images with near-miss queries from sibling categories, and those are re-filtered through the same reranker.

    For datasets involving images, the template system uses three versions: one query evaluating whether the image alone is unsafe, one for the accompanying text alone, and one for the combination, treated as unsafe if either component is. The construction is meant to make the model attend to which part of the input the query is actually about.

    § 09

    Training and checkpoint merging

    The base is Ministral-3-3B-Base-2512, a 3B causal language model from the Mistral 3 family with native multimodal support through a Pixtral vision encoder, so one checkpoint accepts text, images or both.

    Fine-tuning uses LoRA on the language model parameters, with cross-entropy loss on the single output token. Both LoRA and full SFT were run. Full SFT is 0.7 F1 higher on Aegis v2 validation, LoRA is 0.5 higher on the taxonomy validation set, and the report treats the difference as insignificant and adopts LoRA for training efficiency.

    Two checkpoints, then a merge

    Two runs rather than one. Checkpoint P trains on public safety datasets only, excluding the generated taxonomy data. Checkpoint PG trains on public plus generated.

    They are strong in different places. P reaches 88.5 F1 on Aegis v2 validation but only 61.1 on the fine-grained taxonomy set. PG gets 84.4 on the taxonomy set and 87.1 on Aegis v2. The report describes P as well calibrated to standard benchmarks and PG as adding fine-grained discrimination while possibly suffering distribution drift.

    They are merged with spherical linear interpolation, with a 0.1 slice of Ministral-3B-Instruct added. The final recipe is 0.6 PG plus 0.3 P plus 0.1 Instruct, produced through pairwise SLERP merges.

    Adding 0.1 of the instruct checkpoint on its own lifts taxonomy F1 from 61.1 to 65.3 for P and from 84.4 to 84.6 for PG, which the report reads as general instruction-following capability transferring to the safety task. The three-way merge reaches 88.0 on Aegis v2 validation and 88.7 on the taxonomy set, above either parent on the taxonomy side while recovering most of the Aegis gap.

    § 10

    An evaluation built to be different

    Generate training data from a taxonomy, evaluate on a taxonomy, and you may just be measuring memorisation. The evaluation taxonomy was designed separately to reduce that risk, and it differs in structure, naming, grouping, generation models and seed data.

    Training uses 11 super classes and 73 leaves, with variable subcategory sizes. Evaluation uses 12 super classes, 26 subcategories and 52 leaves, with exactly two leaves per subcategory. The evaluation categories are built to four principles: siblings are disjoint so each piece of content maps to exactly one leaf, categories are distinguished by harm type rather than severity, names are concrete and action-oriented rather than legalistic, and every subcategory has at least two children so contrastive pairs can be generated.

    Names and boundaries differ rather than translating. On weapons, training has "Guns and Illegal Weapons" and "Indiscriminate Weapons" while evaluation has "Conventional Weapons" and "WMDs". Fifteen hate-related training leaves become four evaluation leaves. One training crime super class splits into three on the evaluation side. Ten of the twelve evaluation super classes have a loose counterpart in training, and no leaf maps one to one.

    The test set also uses different LLMs and different seed samples for both generation and verification than the training data did. A separate validation set, generated with the same LLMs as the training data, is kept for ablations only.

    The sample construction is flipped relative to training. Training uses iso-content: one document, different queries. Evaluation uses iso-query: one fixed query, with a positive matching the target category and a negative matching a sibling but not the target. Both samples are unsafe, so detecting general unsafety gets you nowhere.

    Evaluation also drops template randomisation. Instead of drawing a phrasing from a pool, it uses one manually authored canonical query per category, 90 in total, applied uniformly. That isolates category-level discrimination from template luck. A second LLM then verifies every sample, checking the label is right and the sample is answerable against the fixed query, and mismatches are discarded.

    Easy to conflate

    The evaluation taxonomy's three severity tiers are metadata describing the categories. They are not the strict, moderate and lenient instruction templates from stage one, which are a training-time device. Training's taxonomy has four severity tiers, evaluation's has three.

    § 11

    Results, including where it loses

    Evaluation spans 16 benchmarks across 21 splits against 10 baselines, with all evaluation samples held out from training.

    Shieldstral averages 84.9 F1 across the text safety benchmarks, tied with GPT-OSS-Safeguard-20B, while being the smallest model in the comparison at 3B against 4B to 20B. On the three multimodal benchmarks it averages 83.8 against 77.6 for OmniGuard-7B, the next highest.

    On the adaptability benchmark it comes second. GPT-OSS-Safeguard-20B scores 94.1 to Shieldstral's 91.3, and the report attributes the gap to per-category policy prompts, reasoning that decomposes an unfamiliar policy into more familiar ones, and roughly seven times the parameters. Shieldstral returns one token instead of a reasoning trace, so the choice between them is an accuracy against latency tradeoff whose value depends on the deployment.

    On the LlavaGuard benchmark, LlavaGuard-7B scores 81.4 and Shieldstral 72.0. Some LlavaGuard test images were unavailable, so every model's score there is computed on the available subset.

    The multilingual picture is uneven

    Twelve languages are officially supported, and the multilingual benchmarks reach further, covering 17 and 28 languages. The report states that Shieldstral underperforms in prompt classification for Arabic and Indonesian as well as other low-resource languages.

    Indonesian is the widest split: 55.5 F1 on prompt classification against 94.1 on response classification. Response scores are also higher for Arabic and for the pooled low-resource group, though not everywhere. English, Chinese and Russian all score slightly lower on response classification than on prompt classification.

    § 12

    Running it yourself

    The weights are Apache 2.0, the model fits in 16GB of VRAM in BF16, and it serves through vLLM, llama.cpp, SGLang or Transformers. The API returns token logprobs rather than a finished score, so the client extracts the yes and no values and renormalises them itself.

    Two things from the card worth carrying into a deployment. It was trained on sequences up to 32k tokens, and although the architecture supports more, the card recommends staying inside that range. And keep <Instruct> constant across a surface. If you do change the instruction or the policy wording, re-check your operating threshold on representative data rather than assuming the old calibration carries over.
